Candidate, Composite & Surrogate Keys in SQL

🟢 Intermediate Level | Database Schema Design

📖 Definition

A Candidate Key is any column (or set of columns) that can uniquely identify a table row. A Composite Key is a primary key formed by combining two or more columns. A Surrogate Key is an artificial, system-generated identifier (such as `AUTO_INCREMENT` or `UUID`).

🤔 Purpose

Simplifies relational joins and handles tables where single columns do not offer natural unique identification.

🌐 Multilingual Explanations

English

Surrogate keys (e.g. `AUTO_INCREMENT INT`) provide fast, artificial integer primary keys. Composite keys combine columns `(student_id, course_id)` for junction tables.

📝 Syntax & Parameters

-- Composite Key in Junction Table
CREATE TABLE student_courses (
    student_id INT,
    course_id INT,
    enrollment_date DATE,
    PRIMARY KEY (student_id, course_id)
);

⚡ Execution Flow

  1. SQL engine validates combined unique tuple `(student_id, course_id)` on insert.
  2. Rejects duplicate pairs while allowing individual non-unique values.
  3. Optimizes join operations across junction tables.

💡 Progressive Examples

Example 1: Composite Primary Key

CREATE TABLE order_items (
    order_id INT,
    item_id INT,
    quantity INT,
    PRIMARY KEY (order_id, item_id)
);

🖥️ Expected Output

Table 'order_items' created with Composite Primary Key (order_id, item_id).

🔍 Line-by-Line Code Breakdown

  • PRIMARY KEY (order_id, item_id): Combines both columns to form a unique composite primary key constraint.

⚠️ Variations & Edge Cases

Surrogate keys (like `UUID`) prevent exposing real-world business entity keys externally.

❌ Common Beginner Mistakes

Allowing Duplicate Pairs in Junction Tables: Creating a junction table without a composite primary key allows duplicate enrollment or item records.

🛠️ Real-World Practical Usage

Many-to-many relationship mapping in SQL databases.
